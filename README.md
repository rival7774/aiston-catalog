# Полка

Мини-каталог на Go, Angular и PostgreSQL. При первом запуске приложение создаёт 200 категорий и 200 000 товаров. Товары есть на каждом уровне дерева.

## Запуск

Понадобится Docker с Compose v2 (на Windows и macOS подойдёт Docker Desktop в режиме Linux-контейнеров). Из корня репозитория выполните:

```sh
docker compose up --build -d --wait
```

Откройте [каталог](http://localhost:8080). Первый запуск скачивает образы, собирает приложение и наполняет БД. Для остановки выполните `docker compose down`. Именованный том сохраняет данные. Команда `docker compose logs api db` показывает ошибки инициализации.

Параметры можно задать в файле `.env` в корне до запуска.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| APP_PORT | 8080 | Порт сайта на хосте |
| API_PORT | 8080 | Внутренний порт Go, одновременно подставляется в конфигурацию nginx |
| DB_NAME | catalog | Имя базы при инициализации тома |
| DB_USER | catalog | Роль при инициализации тома |

PostgreSQL принимает соединения через Unix-сокет в томе, доступном сервисам db и api. Для локального стенда используется доверенная аутентификация сокета, TCP у базы выключен. Наружу опубликован только nginx. Он раздаёт Angular и проксирует запросы `/api/`. Многостадийная сборка оставляет Go-бинарник в scratch и статические файлы в образе nginx.

Compose ждёт готовности основного процесса PostgreSQL. API применяет миграцию и сид в одной транзакции под advisory lock и записывает версию. При прерывании PostgreSQL откатывает всю транзакцию. Готовность API проверяется через БД до старта nginx. При SIGTERM сервер даёт активным запросам до восьми секунд на завершение.

## Модель чтения

`category.parent_id` задаёт непосредственного родителя. Таблица замыканий `ancestry` хранит пары «предок, потомок» и расстояние между ними, включая саму категорию с расстоянием 0. Она строится рекурсивным CTE. Число уровней ограничено только в сиде. Индекс `category(parent_id, id)` обслуживает выдачу соседей и проверку наличия детей. Индекс `ancestry(descendant, depth DESC)` возвращает хлебные крошки от корня. Первичный ключ пары предок–потомок гарантирует единственный путь в дереве.

Для каждого товара в `feed` записана строка для его категории и каждого её предка. Выборка поддерева становится чтением одного упорядоченного диапазона. `category_size` хранит число таких строк по категории, включая её собственные товары. Выдача узлов соединяет счётчик и проверяет наличие детей в одном SQL-запросе. Адресные маршруты отдельно проверяют существование категории, поэтому пустая ветка и отсутствующая категория различимы. На запрос приходится максимум два обращения к БД.

Цена такой схемы — строки проекции на каждом уровне, в том числе копия имени для поиска. Каталог доступен только для чтения. Если появится редактирование товаров или перенос ветвей, проекцию, пути и счётчики потребуется менять в той же транзакции.

## Контракт HTTP

Все маршруты принимают GET и возвращают JSON.

| Маршрут | Результат |
| --- | --- |
| `/api/categories` | Корни дерева |
| `/api/categories/25/children` | Непосредственные дети |
| `/api/categories/25/path` | Путь с выбранной категорией в конце |
| `/api/categories/25/products?limit=50` | Объект с `items` и `nextCursor` |
| `/api/health` | Готовность API и соединения с БД |

Каждый узел содержит `id`, `name`, `hasChildren`, `count`. Товар содержит `id`, `categoryId`, `name`, целую цену `priceKopecks` и время `createdAt` в RFC 3339. Неизвестная категория возвращает 404, некорректные параметры — 400 с телом вида `{"error":"Invalid cursor"}`.

### Прокрутка и поиск

`limit` принимает значения 1–100, по умолчанию 50. Следующий запрос передаёт полученный `cursor` и тот же текст поиска `q`. Значение `nextCursor: null` завершает ленту. Поиск без учёта регистра ищет буквальную подстроку, в том числе символы `%` и `_`. Поле поиска отправляет запрос после паузы 300 мс.

Первичный ключ `feed(ancestor, created_at, product_id)` поддерживает обратный проход B-tree. Условие продолжения — строгое сравнение пары `(created_at, product_id) < (время, id)`. Уникальный ID разрешает совпадения дат. Сервер читает до `limit + 1` строк и формирует курсор по последнему **выданному** товару. Дополнительная строка попадёт в следующую страницу. Base64url-курсор содержит обе координаты, категорию и строку поиска. Гарантия обхода относится к неизменяемому каталогу.

Поиск имеет дополнительный GIN-индекс `feed_search` с `pg_trgm`. Планировщик выбирает план с учётом селективности. Очень короткие подстроки дают мало информации для триграммного индекса.

### Проверка времени ответа

На локальном стенде Windows с PostgreSQL 17.12 через TCP loopback и Go API проверен полный обход 200 000 товаров. На прогретом кеше для страниц по 100 товаров p95 составил 2,68 мс в первых 10 100 позициях каждого корня и 2,72 мс глубже. Максимум среди 2 000 страниц — 4,46 мс. Измерения включали чтение JSON одним последовательным клиентом. Отдельный прогон поиска по отсутствующей однобуквенной подстроке дал p95 31,50 мс на 30 запросах. В этих замерах nginx и Docker не участвовали.

Целевые 100 мс требуют измерения на машине проверяющего. Для просмотра плана откройте psql командой `docker compose exec db psql -U catalog -d catalog` (подставьте значения из своего .env). Пример проверки чтения глубокой страницы:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT p.id, p.name, p.price_kopecks
FROM (
  SELECT product_id, created_at FROM feed
  WHERE ancestor = 1 AND (created_at, product_id) <
    (timestamptz '2025-01-02 00:00:00+00', 46080)
  ORDER BY created_at DESC, product_id DESC LIMIT 51
) f JOIN product p ON p.id = f.product_id
ORDER BY f.created_at DESC, f.product_id DESC;
```

Сравните с первой страницей, убрав сравнение пары. Смотрите на условия индексного доступа, число прочитанных строк и буферов. Время SQL и время полного HTTP-ответа измеряются отдельно.

## Проверка интерфейса

1. Откройте [глубокую ссылку](http://localhost:8080/?category=200) и обновите страницу. Сверьте путь и выделенный узел.
2. Сверните и раскройте предка. В Network повторного запроса детей быть не должно.
3. Включите замедление сети, прокрутите ленту и быстро смените категорию. Старый запрос отменяется. DOM содержит только видимые строки и небольшой запас.
4. Отключите сеть перед догрузкой, затем верните соединение и нажмите «Повторить». Список продолжается с прежней позиции.
5. Введите часть названия, затем заведомо отсутствующее слово. Проверьте завершение ленты и восстановление товаров после очистки поля.

GitHub Actions собирает сервисы, запускает Go-тест курсора и интеграционную проверку через реальный HTTP API. Скрипт `checks/catalog.py` сверяет счётчики, полный обход листа и границу страниц корневой категории с детерминированным сидом.

## Что дальше

Снять p50/p95 HTTP на холодном и прогретом кеше, включая редкие и короткие поисковые строки. Добавить браузерный тест для переключения категории во время запроса. Виртуализация ограничивает DOM, а загруженные страницы выбранной категории пока остаются в памяти до переключения или нового поиска.
